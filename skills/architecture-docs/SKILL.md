# 系统架构文档

为目标项目编写或更新系统架构设计文档。先调查，再写作；以事实为基础，聚焦设计而非代码实现说明。默认只修改文档，不修改业务代码、依赖或部署配置，不主动提交或推送。

## 1. 确定范围并调查项目

1. 确认用户指定的目标项目；未指定时使用当前工作项目，不要将本 skill 所在仓库误当作目标项目。遵循项目自己的文档约定和指令。
2. 阅读 README、现有架构文档、需求说明、设计决策记录和目录结构。
3. 按需检查依赖清单、程序入口、路由或协议定义、核心业务模块、数据模型或迁移、测试，以及部署和 CI 配置。先检索再定向阅读，不必遍历全部代码；不要读取或复制无关密钥与个人数据。
4. 梳理系统边界、技术栈、核心组件、请求和数据流、数据存储、外部依赖及部署方式。对关键事实记录可引用的仓库相对路径，优先引用稳定文件而不是易变化的行号。
5. 区分信息状态：
   - **已实现**：有代码或配置证据。
   - **拟议设计**：来源于明确需求或设计建议，尚未实现；必须标注状态，不能写成现状。
   - **待确认**：证据不足或相互矛盾，使用 `TODO：待确认事项及所需依据`。
6. 现有代码用于说明实现现状，用户需求用于说明目标，两者冲突时记录差距，不擅自改变需求或把计划写成已实现。不要仅凭依赖清单就断言某组件正在使用。

若项目边界或冲突会实质改变整体设计，先向用户提出少量关键问题。其他局部未知项保留 TODO，继续完成有依据的部分。没有实现的新项目只能依据已确认需求编写明确标注的拟议设计。

## 2. 组织文档

默认主文档为 `docs/architecture.md`，新增详细设计统一放在 `docs/architecture/`。

- 先查找现有架构文档，优先更新并保留仍有效的设计，不创建两份内容重复的主文档。
- 若现有主文档不在默认路径，遵循项目明确约定；需要迁移时先确认，并同步更新引用，不擅自删除旧文件。
- 能用几句话、一个表格或一张图说清楚的内容，直接留在主文档。
- 仅在某部分复杂到明显影响主文档可读性时拆分，如认证、调度或存储设计。不要预先创建这些子文档。
- 拆分后主文档必须保留概要与相对链接；子文档负责详细设计，不大段重复主文档。
- 不创建空文档、空章节或仅有占位模板的子文档。不适用的核心章节保留标题，简短说明原因。

## 3. 编写主文档

默认使用用户交流语言，项目有明确语言约定时遵循项目约定。保留下列一级、二级标题及顺序，三级标题按下述要求组织；确需偏离时说明原因。

### `# 系统名称`

使用项目真实名称，而不是字面量“系统名称”。必要时简短注明文档范围和整体设计状态。

### `## 目标`

说明系统解决的问题、核心目标、关键非功能目标，以及明确不解决的问题（如有）。

不编造 SLA、吞吐量、延迟或容量指标。没有明确指标时写定性目标或标为待确认。

### `## 架构设计`

先使用 Mermaid `flowchart` 展示真实核心组件、外部依赖和它们的关系，必要时区分系统内外边界及已实现/拟议组件。箭头应表达实际调用、数据传输或依赖含义，不放无意义的示例图。

#### `### 总体架构`

解释整体工作方式、关键请求/数据流、组件协作方式和关键技术决策。

结合项目实际，覆盖以下方面，可使用短段落或表格，不要求为每项创建章节：

- **高可用与故障处理**：单点、超时、重试、幂等、降级、恢复或备份机制。
- **安全**：信任边界、认证授权、敏感数据和密钥管理。
- **可观测性**：日志、指标、追踪、健康检查及告警。
- **部署与升级**：运行单元、配置、发布方式、迁移和回滚约束。
- **扩展性**：状态归属、扩缩容方式、主要瓶颈和限制。

只描述有依据的机制；缺失的能力应写成当前限制或拟议改进，不得凭空添加集群、队列、缓存等基础设施。单机工具、库或静态站点应采用与其规模相称的描述。

对重要决策说明所选方案、依据、代价及明显替代方案。没有历史依据时不要虚构当时的决策动机；可标注为当前分析或待确认。

#### `### 各组件职责`

使用表格列出核心组件：

| 组件 | 职责 | 依赖 |
| --- | --- | --- |

表格必须填入实际内容，不复制空表作为最终结果。保持组件命名与架构图一致；复杂组件可链接详细设计。

### `## 接口设计`

概述系统核心交互边界，而不是机械地要求所有项目都有 HTTP API。

- HTTP 服务使用“接口 / 方法 / 用途”表格，按需补充认证、关键输入输出及错误语义。
- CLI 使用命令、参数和用途；库使用公开函数或模块边界；事件系统使用主题、生产者/消费者和消息语义。
- 只记录真实接口或明确标注的拟议接口，不编造 `/api/example` 等占位路由。
- 简单接口不复制完整 Schema。复杂接口优先引用现有 OpenAPI、协议文件或独立 API 文档，并保留概要。
- 没有独立对外接口时，明确说明。

### `## 数据模型`

描述核心逻辑实体、关系、所有权及必要的生命周期，不把数据库字段清单直接当作领域模型。

- 有明确实体关系时优先使用 Mermaid `erDiagram`，关系基数应有代码、约束或需求依据。
- 同时提供“实体 / 说明”表格。
- 图中仅保留理解设计所需的关键属性；复杂字段、索引和约束放入必要的详细设计或引用已有 Schema。
- 非关系型存储不要伪造外键；按实际情况描述文档、消息、文件或内存结构，可使用更合适的 Mermaid 图。
- 无持久化或无独立领域实体时说明事实，不为满足格式虚构 User、Project 等实体。

### `## 开发约束`

#### `### 后端`

根据项目实际记录语言及版本要求、框架、数据访问方式、日志方案和关键工程约束。版本只写有依赖或配置依据的内容。

不得混用不兼容的技术栈：Gin、Ent、标准库 slog 属于 Go 生态，不能作为 Python 后端的组合。若项目使用 Python，记录实际 Python 框架与库；若使用 Go，记录实际 Go 组件，不因为本 skill 提及 Gin/Ent/slog 就强行选用。

#### `### 前端`

根据项目实际记录框架、样式、UI 组件、图表、弹窗和国际化方案。不默认强加 Next.js、Tailwind CSS、shadcn/ui、Recharts 或 i18next；只有实际采用或需求明确指定时才记录。

用户可见文本原则上应通过项目的国际化资源管理，避免在业务组件中硬编码中文或英文文案。若项目尚未采用国际化，将其标为建议或待确认约束，不能声称已经实现。

无后端或无前端时，保留对应小节并说明不适用。必要时增加 CLI、SDK 等项目实际需要的三级小节。

## 4. 控制表达和图示

文档重点回答：为什么这样设计、有哪些组件、如何协作和流转数据、核心数据与接口是什么、如何处理故障、如何部署扩容与观测，以及有哪些约束和取舍。

- 不大量复制代码、显而易见的函数细节或依赖清单。
- 所有架构图统一使用 Mermaid：组件关系用 `flowchart`，实体关系用 `erDiagram`，交互用 `sequenceDiagram`，状态变化用 `stateDiagram-v2`，类或领域模型用 `classDiagram`。
- 仅添加有解释价值的图，不要求每种图都出现；每张图聚焦一个问题，不用一张巨图承载所有细节。
- 图表达关系，正文解释设计和取舍，避免重复。必要时在重要描述旁引用依据文件。

## 5. 校验并交付

完成后检查：

- 核心章节齐全且顺序正确；无空章节、占位示例或无意义拆分。
- 组件、技术栈、接口、实体关系和部署描述有依据，图表与正文命名一致。
- 已实现、拟议设计和 TODO 清晰区分；没有把缺失能力写成已实现。
- 仍有效的旧内容已保留，过时描述已修正，未覆盖与任务无关的用户修改。
- 所有文档相对链接、依据路径、Markdown 围栏及 Mermaid 图语法经过检查。
- 优先运行项目已有的 Markdown 检查或 Mermaid 渲染工具。没有工具时进行静态检查，并明确说明未做渲染验证；不要为了校验擅自安装依赖或把私有架构发送到在线服务。
- 检查最终 diff，确认修改范围仅包含本任务所需文档，不包含密钥或其他敏感内容。

向用户简要汇报新增/更新的文档路径、主要设计结论、重要待确认事项，以及实际执行的检查和未验证内容。不要在最终回复中重复整篇文档。
